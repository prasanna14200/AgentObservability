# Day 7: durable local payment safety prototype

Verified: 2026-10-13. This stage adds SQLite persistence and test-only reconciliation. It does not issue buyer consent, call PayPal, enable a real payment adapter, or perform automatic retries. The Day 6 gateway still accepts only marked fake adapters. The existing REST client and its `PayPal-Request-Id` algorithm are unchanged.

## SQLite schema and interfaces

`src/agentsentinel/payment_sqlite.py` implements the Day 5 `AuthorizationRepository.find` and Day 6 `AuthorizationConsumer.claim` plus an operation store extension used by the existing gateway. It opens a new SQLite connection per method. `BEGIN IMMEDIATE` transactions, a primary key on `operations.operation_id`, a unique authorization binding, and conditional state updates coordinate writers across connections and processes. WAL mode and `synchronous=FULL` are configured for a local file. Database errors become value-free `StoreUnavailable` exceptions; the gateway fails closed.

| Table | Stored fields | Excluded data |
| --- | --- | --- |
| `operations` | Operation ID; SHA-256 request fingerprint; bounded principal/scope/intent/merchant IDs; exact amount/currency/action; untrusted target order ID; state; sanitized result JSON; authorization/attempt IDs; stable idempotency key; separately verified provider IDs; update time | Purpose text, credentials, approval URLs, raw provider replies, payment instruments |
| `authorizations` | Application-controlled authorization fields, authenticated principal binding, exact amount/currency/merchant/action/target, issuer, lifecycle and timestamps | Buyer password, tokens, arbitrary AI payloads |
| `operation_events` | Safe state-transition name and timestamp | Exception text and raw request values |

The production module deliberately has **no authorization issuance/import API**. Tests seed fixture records directly through SQL in `tests/unit/test_payment_sqlite.py`; this is not an approval mechanism. A future authenticated buyer-consent service must own issuance and database write permissions. The configured trusted issuer must match stored records. `find` requires authenticated principal, scope, intent, and operation; the policy then checks the remaining exact binding. `claim` rechecks the record, current trusted time, and `issued` status inside a write transaction. `revoke` changes only an issued record bound to the trusted context. Consumed/revoked/expired records cannot be claimed again.

`TrustedGatewayEntryPoint` is a narrow facade whose caller supplies only a `PaymentIntent`; its injected `AuthenticatedContextProvider` supplies principal and scope. Day 7 tests use a fixed test provider. A real application must derive that context from an authenticated session and must not expose the provider, gateway internals, or SQLite file to an AI agent. Python interfaces alone cannot enforce this deployment boundary.

## Transactions, state, and crash recovery

1. `reserve_intent` uses **transaction A** to insert a `RESERVED` operation or return its existing state. The operation fingerprint binds the full validated intent and authenticated context. A changed request with the same operation ID is a conflict. The operation row records only bounded fields needed for recovery, not the free-text purpose.
2. The existing policy evaluates using the trusted repository. `BLOCK` and `REVIEW` finalize the reserved operation as `REJECTED` or `REVIEW_REQUIRED`; neither claims authorization nor calls an adapter.
3. For `ALLOW`, `claim` uses **transaction B** to re-read the reserved operation and authoritative authorization, check principal/scope and exact request binding, atomically mark authorization `consumed`, assign stable attempt and idempotency IDs, and move the operation to `CLAIMED`. A failure rolls back **both** changes. There is no gap between consuming authorization and persisting the claimed state.
4. After transaction B commits, the fake adapter runs **outside** any database transaction. `finish` then stores only a sanitized `COMPLETED` or `UNCERTAIN` result. It never marks completion before the adapter returns a confirmed fake outcome. The existing PayPal request-ID function is reused to associate a stable create or capture key; no REST request is made.

Transactions A and B are separate because the Day 6 gateway reserves before policy evaluation. The persisted states provide a fail-closed recovery strategy: a crash after A leaves `RESERVED`; a crash after B or after a provider could have acted leaves `CLAIMED`. On restart neither state triggers execution. `RESERVED` returns in-progress, while `CLAIMED` returns reconciliation-required uncertainty. A failed local finalization after an adapter call likewise leaves `CLAIMED`; it cannot be retried by resubmitting the operation. A completed or uncertain stored result is replayed safely. There is no automatic stale-lock clearing, payment retry, or inference that a provider call did or did not happen.

The operation states are `RESERVED`, `CLAIMED`, `COMPLETED`, `REJECTED`, `REVIEW_REQUIRED`, and `UNCERTAIN`; `NEW` is the absence of a row. The event table records each committed transition. A caller-proposed capture `target_order_id` is stored separately from `provider_order_id`; the latter is written only after verifier confirmation.

## Reconciliation

`SQLiteReconciler` receives an application-owned `TestOnlyOutcomeVerifier`. Its public `reconcile(operation_id)` method accepts no agent-supplied outcome. It reads a bounded snapshot containing operation, attempt, stable idempotency key, action, and known provider IDs; calls the fake verifier outside a transaction; then atomically checks that the operation and association still match before recording `COMPLETED`, `REJECTED` for verified no payment, or `UNCERTAIN`. Verified capture completion requires both matching order ID and capture ID. A mismatch leaves the operation unchanged. Provider order/capture IDs are retained only when verified. Reconciliation itself never invokes or retries a payment adapter. The test-only verifier is not PayPal verification; a future trusted server-side verifier must read provider status independently and validate merchant, amount, currency, order, capture, and account ownership before returning an outcome.

## Evidence, limits, and next work

Tests use temporary SQLite files and cover persistence after reinitialization, concurrent connections and separate processes, a single fake adapter invocation under concurrent submissions, one-time claim, wrong bindings, inactive/expired/revoked authorization, lock contention, transaction rollback using an injected SQLite trigger, interruption after claim, restart without re-execution, uncertainty, verified reconciliation, forged outcome arguments, mismatched idempotency keys and capture orders, and absence of raw secret markers in the database. The Day 1–6 suite remains intact. Final counts and secret-audit scope are in the Day 7 handoff. Gate C's Isolation Forest failure remains unchanged.

SQLite is a **local prototype**, not a distributed production store. Durability depends on the filesystem, database access controls, backup policy, and SQLite/WAL deployment conditions. The two-transaction sequence intentionally favors non-retryable ambiguous states over availability. The test verifier does not establish real provider truth; the fake adapter does not exercise real idempotency or buyer approval. A real Sandbox execution path still needs authenticated buyer-consent issuance, protected file/service permissions, a trusted PayPal status verifier, provider ID and amount/account checks, operational recovery procedures, and a reviewed gateway/adapter integration. Do not simply replace the fake adapter with the REST client. Stop before Day 8 pending approval.
