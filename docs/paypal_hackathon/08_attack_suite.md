# Day 8 — offline payment safety demonstrations

Run `python scripts/run_attack_suite.py` from the repository root. It imports the existing in-process PayPal spy fixture, uses temporary SQLite files and fake credentials, and never loads `.env` or opens a network connection. The command prints a pass/fail table, exits nonzero on a failed scenario, and writes [the latest results](../attack_suite_results.md). “PayPal calls” counts only calls after the attack attempt begins; the duplicate and timeout scenarios first make one allowed setup call to the spy.

The amount, merchant, missing, forged, replayed, and expired authorization cases demonstrate that proposals cannot replace a trusted, exact-bound, live authorization. The duplicate capture case returns the stored result without another call. The timeout case remains UNCERTAIN without retry. The prompt-injection case makes a scripted naive agent obey hidden product text by proposing a higher amount and another merchant; the trusted authorization remains unchanged, so the gateway blocks it. The amount threshold and internal advisory signal produce REVIEW without execution. A failed store reservation fails closed.

Day 8 adds exact `SafetyLimits` for operation and trace attempts and daily and per-merchant USD capture budgets. Counts and payment states are durable in SQLite. The budget query counts RESERVED, CLAIMED, UNCERTAIN, and COMPLETED capture operations; completed captures use their original UTC reservation day, while unresolved holds carry into later days until reconciled. `BEGIN IMMEDIATE` covers the check and new reservation together. Loop attempts return `LOOP_LIMIT_EXCEEDED` plus `OPERATION_LOOP_LIMIT` or `TRACE_LOOP_LIMIT`; budget blocks return `BUDGET_EXCEEDED` plus `DAILY_BUDGET_LIMIT` or `MERCHANT_BUDGET_LIMIT`. Create-order requests do not spend capture budgets. The agent-facing facade accepts only an intent; a trusted application provider may add a review signal. Existing hard BLOCK reasons take precedence.

These are controlled simulations, not a measure of real-world prompt-injection coverage. Python component boundaries are not deployment isolation. The limits are application configuration and must be consistent across all processes using a database; the attempts and spending ledger are SQLite durable. A blocked pre-reservation attempt is recorded in the attempt counter but has no payment operation row. Reconciliation and operator review remain necessary for UNCERTAIN results. Order A's unresolved provider 404 and the Day 7 production-control limitations remain open.
